SPECTER — ACCURACY & BENCHMARKING NOTES (for pitch / judge Q&A)
==================================================================

THE QUESTION TO EXPECT: "How accurate is this? How do you know?"

Short answer to lead with:
  "CVE detection is ground-truth accurate against OSV.dev. Secret detection
   is heuristic and benchmarked for precision/recall against a labeled test
   set, the same approach tools like gitleaks and trufflehog use. The
   composite 0-100 threat score is a relative risk indicator, not a
   calibrated prediction, and we don't claim it's 'accurate' in a
   statistical sense — what's verifiable is the findings that feed it."

------------------------------------------------------------------
1. THE THREAT SCORE ITSELF IS NOT BENCHMARKABLE — SAY THIS UP FRONT
------------------------------------------------------------------
The 0-100 score is a hand-weighted sum of findings across all five
scanners. There is no ground-truth "correct" threat score for a given
repo to validate it against — no external dataset says "lodash should
score exactly 42." Don't try to defend the number itself. Defend the
individual findings that produce it, and be upfront that the score is
a relative risk indicator (useful for comparing two scans of the same
repo, or roughly ranking repos), not a calibrated probability.

------------------------------------------------------------------
2. SPLIT THE FIVE SCANNERS INTO TWO ACCURACY CLASSES
------------------------------------------------------------------

A) GROUND-TRUTH VERIFIABLE (quote a hard number here)

   DepChain (CVE matching):
     OSV.dev IS the ground truth. Build a small fixture set of repos /
     package.json snippets pinned to package versions with KNOWN,
     published CVEs (e.g. minimist <1.2.6 prototype pollution,
     lodash <4.17.21, event-stream 3.3.6 itself). Run DepChain against
     them and confirm:
       - 100% detection on the vulnerable pinned versions
       - 0% false positives on the patched versions
     This is not "does DepChain detect novel threats" (it structurally
     can't — see section 3). It IS a fully legitimate, fully verifiable
     claim: "our registry-resolution + OSV query pipeline correctly
     reports what OSV already knows, with zero false positives on our
     test set."

   LayerScan (Dockerfile rules):
     Rule-based against known-bad / known-good Dockerfile patterns
     (:latest tag, curl|sh, secrets in RUN/ENV, missing USER, etc.).
     Same approach: build ~10-15 fixture Dockerfiles, confirm each rule
     fires/doesn't fire as expected.

B) HEURISTIC — NO GROUND TRUTH EXISTS, MEASURE PRECISION/RECALL
   AGAINST A LABELED SET YOU BUILD

   GhostCommit / EnvTrace (secret + entropy detection):
     This is exactly the problem gitleaks and trufflehog solve, and
     both publish benchmark corpora for it. Build a small labeled set:
       - N commits with deliberately planted fake secrets (true
         positives)
       - M clean commits with no secrets (false-positive check)
     Run GhostCommit, report:
       - Recall  = true positives caught / total planted secrets
       - False-positive rate = false hits / clean lines scanned
     This also validates (or invalidates) the entropy threshold (4.5)
     empirically instead of asserting it's correct.

   APIBleed (auth heuristic):
     Weakest of the five — "has auth" is a keyword-proximity guess,
     not a real auth-flow analysis. Recommend explicitly framing this
     one as best-effort in the pitch rather than quoting an accuracy
     number for it, since a fair labeled benchmark is much harder to
     construct honestly here.

------------------------------------------------------------------
3. THE HARD LIMIT TO BE HONEST ABOUT: KNOWN-CVE VS NOVEL COMPROMISE
------------------------------------------------------------------
DepChain only flags what OSV.dev has already catalogued. The two demo
repos (event-stream 2018, node-ipc 2022) are real supply-chain attacks
where malicious code was published as a version bump to an already-
trusted package — not visible in the consuming repo's own commit
history, and not in OSV until days/weeks after public disclosure.

If asked "would this have caught event-stream on day zero" — the
honest answer with the current implementation is NO. It catches it
NOW, retroactively, because OSV has since backfilled the entry. Don't
oversell this. Frame it as: "we correctly catch every disclosed CVE in
your dependency tree, in real time, which most teams don't do at all
today — closing the zero-day gap is the next layer (heuristic
install-script / typosquat detection, roadmapped)."

------------------------------------------------------------------
4. TALKING POINT TO ACTUALLY SAY OUT LOUD
------------------------------------------------------------------
"We validated DepChain against N repos with known, disclosed CVEs —
100% detection, 0 false positives on patched versions, cross-checked
against OSV.dev directly. We validated GhostCommit's secret detection
against a planted-secret test set at [X]% recall and [Y]% false-
positive rate, using the same benchmarking approach industry tools
like gitleaks use. The composite score is a relative risk indicator
built from those verified findings, not a black-box prediction."

MEASURED (npm run benchmark, 2026-09-25; details in
scripts/benchmark/RESULTS.md):

  DepChain: 12 known-vulnerable package versions (event-stream 3.3.6,
  ua-parser-js 0.7.29, node-ipc 10.1.1, minimist 1.2.5, lodash 4.17.20,
  ...) and their 12 patched releases. 12/12 detected, 0/12 reported on
  the patched version, 0 advisories invented; exact agreement with
  OSV.dev on all 24 versions (81 advisories).

  GhostCommit: 25 planted fake secrets, 59 clean lines (15 of them
  secret-looking). Recall 84% overall (95% on vendor-format keys, 40% on
  unstructured passwords/hex tokens). 0 false positives on ordinary code;
  10 of 15 secret-looking non-secrets flagged (integrity hashes, public
  keys, .env.example placeholders). Precision 68%.

So the talking point, filled in:

  "DepChain: 12 of 12 known-vulnerable versions caught, zero false
   positives on patched versions, exact agreement with OSV.dev.
   GhostCommit: 84% recall on a planted-secret test set, 95% on
   vendor-format keys; zero false positives on ordinary code, but it
   over-flags hashes and placeholders, so treat it as a first pass."

The benchmark also confirmed the entropy-threshold concern from section
2: a pure-hex secret can never exceed 4.5 bits/char, so it is only caught
when its variable name matches a pattern (e.g. AUTH_TOKEN=).

Re-run before quoting numbers: DepChain's depend on OSV.dev's live data.

------------------------------------------------------------------
5. PACKAGE VERDICT ENGINE (issue #26; npm run eval-verdicts, 2026-09-26;
   details in scripts/eval-verdicts-results.md)
------------------------------------------------------------------
Separate from the repo scanners above: analyzePackage(name, version)
(#27/#28) gives a pre-install allow/warn/block verdict for one npm
version, from registry metadata + OSV — before anything is cloned or
installed.

  Known-malicious: 19 versions, discovered live from OSV.dev (a MAL- id
  or a CWE-506 "Embedded Malicious Code" advisory) across 16 well-known
  attack names (event-stream, node-ipc, ua-parser-js, coa, rc,
  eslint-scope, flatmap-stream — 9 of the 16 candidate names had no OSV
  malicious-package advisory at run time and contributed no cases).
  19/19 caught, all blocked outright.

  Popular packages: 208 packages from the app's own typosquat list
  (src/lib/scanners/popularPackages.ts), each at its current `latest`
  release. 3/208 (1.4%) flagged, 0 wrongly blocked. The 3 are angular
  1.8.3, hapi 18.1.0 and apollo-server 3.13.0 — each `latest` on an
  unmaintained major with a real disclosed high-severity CVE, so these
  read as correct warns on an EOL release rather than false alarms;
  still worth a second look before the next tier tightens the bar.

Talking point:

  "The verdict engine caught 19 of 19 known-malicious npm versions
   discovered live from OSV, all as an outright block, with a 1.4%
   flag rate on 208 popular packages at their current release — and
   every one of those 3 flags was a real disclosed CVE on an EOL
   major, not a wrong call."

Bug found and fixed by this run: youngDependencySignal's monorepo-
sibling exemption only recognised a *shared* npm scope. It did not
recognise a package whose own scope is named after an UNSCOPED parent
(typescript -> @typescript/typescript-linux-x64, the native-binary
release pattern esbuild/swc/rollup also use), so typescript@7.0.2's own
~20 platform binaries were each flagged "young dependency" and the
package came back block. Fixed in deprisk.ts; re-verified against the
DepChain benchmark in section 4 with no regression.

Only the "metadata" tier (#27+#28) exists yet. Re-run after the diff,
LLM and sandbox tiers (#39/#43/#45) land to see each one's effect.

Re-run before quoting numbers: both sets are discovered/fetched live
(OSV's malicious-package feed, and each popular package's current
`latest`), so exact versions and counts can shift between runs.
